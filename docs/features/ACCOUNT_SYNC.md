# X-Center ID and Aurea settings

Aurea has optional account features for moving preferences between installations and finding a TV the user has approved for pairing. Local controls and PIN pairing remain available without an account. The hosted site and native account entry points must be enabled after staging. The native gate is `EXPO_PUBLIC_AUREA_ACCOUNTS_ENABLED=1`. The GitHub build jobs read it from the repository variable `AUREA_ACCOUNTS_ENABLED`. Leave the variable unset until the production account endpoint has been validated.

## Settings and sign-in

The phone remote and hosted web remote share a private settings backup for remote layout and touchpad navigation. The TV has a separate private backup for language, wallpaper, motion, music tint, glass and blur. Backups can be viewed, restored, replaced or deleted explicitly. The server validates a fixed schema and uses revision checks before allowing writes. Each device keeps its local preferences while signed out or offline. Dock, input mappings, viewing history, Android TV Remote Service credentials and saved remote credentials are outside the sync schema.

The registered Website app uses `https://aurea.xcenter.it/account/callback`. Its portal status is active and Verified app. Public DNS confirms the ownership record at `_xcenter-id.aurea.xcenter.it`.

- Hosted web receives a Secure, HttpOnly, SameSite product session cookie. A browser-bound state cookie protects the authorization callback.
- The native phone uses the system authentication sheet on iOS and a Custom Tab on Android. The app generates a random pickup proof and sends its SHA-256 challenge to the Aurea backend. The exact HTTPS callback stays on the website. The phone proves the original secret to redeem its one-time sign-in and stores the resulting Aurea bearer in SecureStore. Successful iOS pickup dismisses the sign-in sheet. On Android, return to the remote after completing the browser step.
- The TV signs in by QR or device code and encrypts its scoped Aurea session on the TV with Android Keystore. The device-code redemption also requires its original pickup proof. A household can have up to eight TV-local profiles. Each profile links one X-Center ID, and the same ID can be linked to only one profile on the same TV. Switching profiles changes the active account and the launcher’s wallpaper, motion, music tint, glass, blur and language. The Home profile keeps the pre-existing settings. Dock, input mapping, viewing history and the classic launcher retain their existing TV-wide storage.
- The backend validates the issuer, signed ID token, nonce and subject. It performs authorization-code exchanges with S256 PKCE. Web, phone and TV product sessions are scoped to their respective endpoints. Without **Stay signed in**, the product session expires with its issuer access token, up to one hour. Opting in on TV, phone or web requests renewable credentials. On the single account service, issuer credentials stay server-side and are stored in an encrypted state directory. Authorized requests renew expiring access tokens through one exchange at a time, with a 14-day idle limit. A denied or uncertain exchange requires reauthentication. Local preferences and previously issued TV remote credentials remain accessible.

The account UI is isolated from preview data. The remote and TV may display English account copy where a translation is unavailable.

## Pair an approved TV

1. Sign in on the TV and the phone or hosted web remote with the same X-Center ID.
2. On the television, open its X-Center ID settings and select **Allow a remote to pair**. This authorizes one remote for 90 seconds. The hosted remote connection must be ready before the invitation opens.
3. In the remote’s settings, choose **Find approved TVs** and select the TV.
4. The TV issues a separate remote credential. The remote saves it in its existing vault and can reconnect with that credential without reusing the account invitation.

This pairs Aurea Home. System controls that work inside other Android TV apps continue to use the Android TV Remote Service pairing already offered by Aurea Remote. On the TV, **Manage account-paired remotes** can revoke an individual account-paired remote. The remote’s existing **Forget this television** can remove its own authorization while the TV is online. The launcher’s existing revoke-all action remains available.

## Same-account automatic pairing

On the TV, turn on **Automatic pairing** for the active household profile. When the launcher is active and the hosted connection is ready, it publishes a renewable short invitation scoped to that account. A signed-in phone or web remote without a current TV can automatically select an unambiguous invitation. If several TVs are available for automatic pairing, use **Find approved TVs** to choose. The TV issues its own revocable credential. The account session is still subject to expiry and may require signing in again. Revoking an account-paired remote on the TV turns off that profile's automatic pairing.

## Trust boundaries

The account service retains the TV label, opaque device and peer IDs and a one-use grant in memory for the invitation lifetime. The shared account’s server-verified subject gates discovery and grant pickup. The service rechecks the identity-provider session for those requests. Listing devices never returns the grant. Pickup consumes the grant in the account service. The remote verifies the TV identity on the existing WebRTC channel before sending it. The TV checks its own monotonic deadline, bridge origin and loopback proof and consumes the grant once before issuing device trust. The actual remote credential stays on the TV and the paired remote. Closing an invitation locally invalidates it even if its cloud listing temporarily remains visible. Account pairing depends on the existing trusted production signaling endpoint. Someone with access to the signed-in X-Center ID can claim an open invitation. Only enable automatic pairing for an account you control. Account sign-out does not revoke already issued device trust. Revoke those devices on the TV.

Relevant code includes `server/account/http.mjs`, `server/account/oidc.mjs`, `server/account/invitations.mjs`, `src/remote/account/` and the Android `AccountInvitation`, `TVPlatform` and `HomeRemoteServer` classes. These changes affect UADS-SEC-003 and UADS-SEC-004. Local HTTP and Android trust-boundary tests cover invalid origins, proof mismatches, expiry, cancellation, replay, account separation and rejecting a mismatched TV. The deployed issuer’s passkey, physical FIDO key, revocation and actual browser/native/device behavior still need verification.

## Staging and rollback

The account process binds to loopback port 8793. Use `deploy/aurea-account.service` with an isolated, immutable server snapshot and its locked production dependencies. Set `AUREA_ACCOUNT_ENABLED=1`, `AUREA_XCENTER_CLIENT_ID` and `AUREA_XCENTER_CLIENT_SECRET` in the root-only `/srv/xcenter/secrets/aurea/account.env` service configuration. Use a credential provisioned directly into protected configuration. The service unit uses the appliance’s existing Node 24 runtime. The existing PeerServer unit and its deployment are independent.

Stage without a public route, run the server tests and verify its dependency load, start the loopback service with valid credentials, and verify a JSON response from `/account/session`. Add the `/account/` proxy only after staging succeeds. It does not log callback queries because they can contain one-time authorization codes. Validate and reload Nginx, verify the HTTPS session endpoint, then test real account consent, private backup and restore, cross-account isolation, phone sign-in and TV invitation and revocation. To roll back, revert the account proxy, reload Nginx and stop only the account service. Service restarts clear short sessions and invitations. Renewable sessions survive in the systemd-managed private state directory. The account process must have exclusive access to it. Changing the registration secret invalidates persisted sessions. The process removes the previous encrypted token before requesting its replacement so a restart cannot replay a potentially consumed token. Backup records are held by X-Center ID and are unaffected by Aurea restarts.
